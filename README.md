# n8n Workflow Lab

**Тема:** Low-code автоматизация бизнес-процессов и интеграция информационных систем на примере n8n.  
**Формат:** самостоятельная лабораторная работа с готовым окружением, автотестами и обязательным видеоотчетом.  
**Трудоемкость:** ориентировочно 7-8 часов для обязательной части, до 10–11 часов с дополнениями.

## Контекст и результат

Представь, что служба поддержки получает обращения, а информация о пользователях и регистрация заявок находятся в разных сервисах. Нужно связать их с помощью визуального workflow в **n8n**, не создавая отдельный backend. Система должна принять обращение, проверить поля, найти пользователя через REST API, определить ответственную группу и SLA, зарегистрировать обращение и вернуть JSON с результатом. При сбоях - вернуть корректную ошибку.

В ходе работы ты познакомишься с некоторыми node (узлами), доступными в n8n и отладкой получаемого workflow. Предоставляемые материалы - достаточны для выполнения всего задания, однако для получения экспертного уровня освоения материала, понадобиться проявить смекалку.

## Необходимые инструменты (Если есть нужно помощь с установкой, то напиши нам)

- Docker Desktop / Docker Engine с Compose v2.
- Python 3.10 или новее для запуска тестов.
- браузер и Git (GitHub для финальной сдачи).

## Быстрый запуск

Для выполнения и сдачи задания сначала создай **Fork** репозитория `low_code_n8n_topic` в своем аккаунте GitHub, затем клонируй свою копию. Если пока хочешь только ознакомиться с проектом, можно скачать ZIP через **Code → Download ZIP**. Открой терминал **в корневом каталоге** проекта и выполни (обрати внимание, что для запуска нужно освободить порты 8080 и 5678):

```shell
docker compose up -d
```

После запуска, чтобы перейди по следующим ссылкам, чтобы проверить корректность работы:

- n8n: http://localhost:5678 (при первом запуске создай локальный аккаунт).
- Mock API: http://127.0.0.1:8080/health.
- пример пользователя: http://127.0.0.1:8080/users/451.

В n8n по очереди импортируй **три учебных workflow**: `workflows/tutorial-basics.json`, `workflows/tutorial-items-loops.json`, `workflows/tutorial-webhook.json` и выполни упражнения из [практикума](docs/N8N_BASICS.md). Затем в **отдельный** workflow импортируй `workflows/student-starter.json` и реализуй [основное ДЗ](docs/ASSIGNMENT.md). Чтобы это сделать, необходимо создать личный аккаунт (смотри инструкцию выше), а затем в левом верхнем углу нажать на иконку '+' и создать новый workflow, после чего откроется чистая среда, чтобы загрузить в нее нужный учебный или рабочий json, нужно нажать на троеточие возле "Personal/{название нового workflow}" и выбрать функцию "import -> from file", указав нужный json. Если не создавать отдельные worflow, то все они сольются воедино и результат работы может отличаться от предполагаемого.

**Особености при выполнении ДЗ**:
Рабочий Webhook должен иметь метод `POST` и путь `support-request` (уже настроено в шаблоне). Тесты обращаются к `http://localhost:5678/webhook/support-request`, чтобы они отработали коректно, необходимо сохранить и **опубликовать** workflow (кнопка "Publish" справа сверху). Публиковать нужно только один worflow за раз, иначе они могут мешать работе друг друга, поэтому требуется отпубликовывать старые workflow, если хочешь запустить новый.

## Что должно получиться

**Вход:**

```json
{"requestId":"REQ-1024","userId":451,"type":"technical","priority":"high","description":"Не работает авторизация"}
```

**Успешный ответ HTTP 201:**

```json
{"requestId":"REQ-1024","status":"registered","assignedGroup":"Technical Support","slaHours":1,"userName":"Иван Иванов"}
```

Обращение должно реально сохраниться в Mock API, а не только вернуться в HTTP-ответе. Для ошибок входа/внешних сервисов предусмотрены HTTP 400, 404 и 502 согласно [контракту](docs/API_CONTRACT.md).

## Автоматические проверки

Из корня проекта выполни, чтобы прошли автоматические проверки:

```shell
python tests/run_tests.py --mode base
```

Для экспертного уровня:

```shell
python tests/run_tests.py --mode expert
```

Результаты сохраняются в `reports/latest-results.md` и `reports/latest-results.json`. Прохождения автоматических тестов будет достаточно, чтобы доказать работу функциональных требований workflow, поэтому дополнительные ручные запросы - не нужны.

Функциональная часть оценивается **18 группами на 60 баллов**. Остальные баллы выставляются экспертом: **25 за обязательное видео**, 10 за письменный отчет, 5 за оформление схемы. **Б / Б+ / П** зависят от качества одного и того же базового задания; **Э** требует уровня П и всех 8 экспертных проверок. При отсутствии доступного видео сдача не завершена.

## Структура репозитория

```text
low_code_n8n_topic/
├── compose.yaml                # готовые n8n и Mock API
├── workflows/
│   ├── tutorial-basics.json       # данные, expressions, If/Switch, HTTP
│   ├── tutorial-items-loops.json  # несколько items, циклы
│   ├── tutorial-webhook.json      # вебхуки и HTTP-ответы
│   └── student-starter.json    # заготовка основного задания
├── mock-api/server.py          # готовый имитатор внешних систем
├── tests/run_tests.py          # проверка результата через HTTP
├── docs/
│   ├── ASSIGNMENT.md           # постановка
│   ├── API_CONTRACT.md         # вход, выход, HTTP API
│   ├── N8N_BASICS.md           # практикум
│   ├── SETUP.md                # окружение
│   ├── TEST_RUNNER.md          # запуск проверок
│   ├── TEST_CASES.md           # тесты и баллы
│   ├── GRADING.md              # критерии оценивания
│   └── SUBMISSION.md           # сдача работы
├── submissions/                # сюда положить экспорт собственного workflow
├── REPORT.md                   # шаблон письменного отчета
└── .github/pull_request_template.md
```

Для выполнения ДЗ нельзя изменять Mock API или исходные автотесты с целью обхода требований. Если есть увереность в том, что требование выполнено, но автотесты не проходят, то напиши нам, разберемся =)

## Проверка самого учебного репозитория

В репозитории также предусмотрена автоматическая проверка целостности работы MOCK API, которая выполняется через CI, но ее также можно выполнить вручную:

```shell
python -m unittest discover -s tests -p "test_*.py"
```
Если падают данные тесты, то скорее всего проблема не в твоем workflow, поэтому напиши нам, мы посмотрим, что не так

## Сдача

**Каждый студент работает независимо в своем Fork репозитория `low_code_n8n_topic`.** Исходный репозиторий содержит материалы задания и не изменяется при сдаче работ. Не нужно отправлять свое решение напрямую в его `main`.

Подготовь экспорт **своего** workflow `submissions/support-request-workflow.json` (workflows/student-starter.json - всего лишь шаблон, но можно дорабатывать и его, главное сообщи об этом в отчете), заполни `REPORT.md`, запиши видеоотчет с успешным и ошибочным сценариями, запусти тесты и создай Pull Request из своего Fork в исходный репозиторий. **PR используется только для проверки: эксперт оставляет комментарии и после оценивания закрывает его без Merge.** Поэтому решения других студентов не затрагивают твою работу, а исходный репозиторий остается неизменным.

Все шаги: [SUBMISSION.md](docs/SUBMISSION.md).

## Типичные проблемы (если сталкиваешься с какими-то еще проблемами, то напиши нам)

| Симптом | Что проверить |
|---|---|
| Webhook отвечает 404 «not registered» | Сохранен ли и опубликован ли нужный workflow; используете ли Production URL |
| Ответ содержит `TODO` | Выполняется стартовая заготовка, основная логика еще не реализована |
| Mock API не отвечает из HTTP Request | В контейнере нужен `http://mock-api:8080`, не `localhost:8080` |
| Тесты не находят регистрацию | Действительно ли был вызван `POST /requests` с правильными полями |
| После перезапуска пропали обращения | Mock API хранит тестовые записи в памяти, это ожидаемо |
| Перестали работать все тесты после импорта | Проверьте, какой из workflow сейчас опубликован |

Подробнее: [SETUP.md](docs/SETUP.md) и [TEST_RUNNER.md](docs/TEST_RUNNER.md).

## О работе с данными

**Очень важный момент**: Ты работаешь в локальном окружении n8n, поэтому снос контейнера (например через docker compose down) уничтожит твои наработки, поэтому либо не уничтожай его, либо предварительно выгрузи JSON наработок своего workflow, чтобы потом можно было переподнять контейнер и экспортировать их обратно.
