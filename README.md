# n8n Workflow Lab

**Тема:** Low-code автоматизация бизнес-процессов и интеграция информационных систем на примере n8n.

В лабораторной работе студент знакомится с n8n и создает автоматический процесс обработки обращений пользователей: принимает JSON через Webhook, проверяет поля, обращается к справочнику пользователей по REST API, определяет ответственную группу и SLA, регистрирует результат и обрабатывает ошибки.

В экспертной части предлагается самостоятельно реализовать **Retry при HTTP 503** и **защиту от повторной регистрации по `requestId`**. Готовые механизмы в стартовой заготовке отсутствуют.

> **Текущий статус: этап 5.** Локальное окружение и основной успешный сценарий эталонного workflow были проверены на Windows у автора задания. Тестовый раннер подготовлен и проверен против локального HTTP-симулятора с настоящим Mock API. **На опубликованном эталонном workflow n8n полный набор из 18 тестов еще требует запуска и подтверждения.** Содержание обучающего workflow будем редактировать позже; это еще не окончательная версия учебного репозитория.

## Быстрый запуск

Нужны Docker Desktop/Engine c Compose v2 и Python 3.10+. Студенту **не нужны** платная подписка n8n, API-ключи и регистрация во внешних сервисах.

```shell
docker compose up -d
```

Далее:

1. Откройте [n8n](http://localhost:5678) и при первом запуске создайте локальную учетную запись.
2. Изучите пример [`workflows/tutorial-basics.json`](workflows/tutorial-basics.json) (импорт через **Import from File**).
3. Импортируйте [`workflows/student-starter.json`](workflows/student-starter.json).
4. Замените ответ `TODO` своим workflow в соответствии с [контрактом API](docs/API_CONTRACT.md).
5. Сохраните и **опубликуйте** workflow. Для тестов используется **Production URL** `POST http://localhost:5678/webhook/support-request`.
6. Запустите автоматические проверки:

```shell
python tests/run_tests.py
```

> **Важно:** только **один** workflow с путем `support-request` должен быть опубликован. При импорте эталонного workflow эксперт должен отключить студенческий и наоборот.

### Тестовый запуск дополнительных заданий

```shell
python tests/run_tests.py --mode expert
```

Проверка всей функциональности одной командой:

```shell
python tests/run_tests.py --mode all
```

Раннер проверяет реальные HTTP-ответы и записи в Mock API. После завершения доступны `reports/latest-results.json` и `reports/latest-results.md`. Во время тестов не работайте параллельно с Mock API: раннер очищает тестовые данные перед каждым сценарием.

## Ожидаемый результат

При успешном выполнении обязательной части отправка обращения:

```json
{"requestId":"REQ-1024","userId":451,"type":"technical","priority":"high","description":"Не работает авторизация"}
```

возвращает `HTTP 201` и ответ:

```json
{"requestId":"REQ-1024","status":"registered","assignedGroup":"Technical Support","slaHours":1,"userName":"Иван Иванов"}
```

Соответствующая запись должна быть сохранена в Mock API. При некорректных данных или ошибках API возвращается предусмотренная ошибка вместо ложного сообщения об успехе.

## Оценивание

- **60 баллов**: 18 групп автоматических функциональных тестов.
- **25 баллов**: обязательный видеоотчет (без него сдача считается незавершенной).
- **10 баллов**: письменный отчет.
- **5 баллов**: читаемость и оформление workflow.

**Б / Б+ / П** определяются качеством выполнения общего базового задания. **Э** требует выполнения уровня П и прохождения всех 8 дополнительных тестов (Retry и защита от дубликатов). Тестовый раннер **не** выставляет итоговую оценку, поскольку 40 баллов оценивает эксперт вручную.

Полная шкала - [GRADING.md](docs/GRADING.md). Каждый тест и его вес описаны в [TEST_CASES.md](docs/TEST_CASES.md).

## Проверка инфраструктуры

В браузере на хосте: [n8n](http://localhost:5678), [Mock API](http://127.0.0.1:8080/health), [тестовый пользователь](http://127.0.0.1:8080/users/451).

**Из n8n**, находящегося в Docker, Mock API доступен по адресу `http://mock-api:8080`. Использование `localhost:8080` внутри узла HTTP Request ошибочно.

Сначала можно отдельно проверить вспомогательные компоненты:

```shell
python -m unittest discover -s tests -p 'test_*.py' -v
python tests/smoke_mock_api.py
```

Для выполнения самих функциональных проверок обязательна публикация workflow с методом POST и путем `support-request`.

## Важные ограничения

Это **только локальное учебное окружение**. Не открывайте его порты наружу и не добавляйте в workflow реальные секреты. Тестовые данные Mock API хранятся в памяти и сбрасываются при перезапуске сервиса.

Эталонный workflow и внутренняя проверка раннера находятся в **отдельном закрытом комплекте эксперта**; в публичный репозиторий их включать нельзя.

Последующие шаги проекта: провести полный запуск 18 тестов на настоящем эталонном workflow n8n, улучшить обучающий workflow, подготовить постановку ДЗ и шаблоны сдачи, затем пройти весь путь студента с нуля.
