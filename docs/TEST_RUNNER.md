# Автоматическая проверка workflow

Этот тестовый раннер проверяет **поведение** опубликованного workflow в n8n. Он не анализирует расположение узлов и не требует доступа к внутренней базе n8n. Для работы нужен только Python **3.10+** (сторонние Python-библиотеки не требуются).

## 1. Перед запуском

1. Из корня проекта запустите сервисы: `docker compose up -d`.
2. Откройте `http://localhost:5678`.
3. Импортируйте или откройте проверяемый workflow, **сохраните и опубликуйте** его.
4. Убедитесь, что в узле Webhook указан метод `POST` и путь `support-request`.
5. Если вы импортировали учебную заготовку и эталон одновременно, **опубликуйте только один из них**: путь Webhook у них одинаковый.
6. Закройте другие скрипты и не отправляйте запросы в Mock API во время тестирования.

> Важно: раннер выполняет `POST /__test__/reset` перед независимыми сценариями, **удаляя тестовые обращения и настройки ошибок** Mock API. Он **не** удаляет workflow и настройки n8n.

## 2. Запуск

Из корня репозитория в PowerShell, Windows Terminal, macOS или Linux:

```shell
python tests/run_tests.py
```

В Windows при необходимости замените `python` на `py -3`.

Проверка дополнительных заданий:

```shell
python tests/run_tests.py --mode expert
```

Одновременно проверить обязательную и экспертную части:

```shell
python tests/run_tests.py --mode all
```

Пример вывода:

```text
[PASS] VAL-01   Валидация         3/3
[PASS] VAL-02   Валидация         3/3
...
[PASS] ERR-02   Ошибки API        5/5

Функциональность: 60/60 баллов
```

`PASS` означает, что **все подслучаи** данной тест-группы выполнены. Если хотя бы один не прошел, баллы за группу не начисляются, а рядом с `FAIL` показывается причина.

## 3. Где посмотреть результаты

После выполнения создаются файлы:

- `reports/latest-results.json` - машинно-читаемые результаты, длительность и описание каждой проверки;
- `reports/latest-results.md` - таблица для просмотра человеком.

В отчете рассчитываются только **60 функциональных баллов** и статусы экспертных проверок. Остальные 40 баллов (видео, письменный отчет, организация workflow) выставляются экспертом отдельно. **Тестовый раннер не присваивает уровень Б, Б+, П или Э автоматически.**

Сформированные файлы находятся в `.gitignore`. Для сдачи итоговый результат можно перенести в `REPORT.md`, который будет предоставлен в финальной версии задания.

## 4. Что именно проверяется

**18 обязательных групп**: `VAL-01...04`, `USR-01...02`, `ROUTE-01...04`, `SLA-01...03`, `REG-01...03`, `ERR-01...02`. Суммарно **60 баллов**.

**8 экспертных проверок**: `EXP-R01...05` (повторы вызова `POST /requests` с ограничением и интервалами) и `EXP-D01...03` (последовательные повторные обращения). Прохождение всех восьми - одно из условий уровня Э, наряду с требованиями уровня П.

Полные критерии и входные сценарии: [TEST_CASES.md](TEST_CASES.md); общая шкала: [GRADING.md](GRADING.md).

## 5. Полезные параметры

```shell
python tests/run_tests.py --help
python tests/run_tests.py --mode all --verbose
python tests/run_tests.py --timeout 40
python tests/run_tests.py --output-dir my-results
python tests/run_tests.py --webhook-url http://127.0.0.1:5678/webhook/support-request --mock-url http://127.0.0.1:8080
```

Стандартные адреса совпадают с конфигурацией Docker Compose. При проверке иной конфигурации изменяйте их через параметры, а не редактированием исходного кода раннера.

## 6. Как разбирать ошибки

| Симптом | Что делать |
|---|---|
| `404 ... webhook ... not registered` | Опубликовать workflow; использовать **Production URL**, а не Test URL |
| Возвращается `TODO` | Опубликован студенческий стартовый workflow, который еще не реализован |
| `Нет соединения` с Mock API | Проверить `docker compose ps` и `http://127.0.0.1:8080/health` |
| Ответ 200 вместо 201 | Проверить настройку узла Respond to Webhook |
| В ответе успех, но тест регистрации падает | Проверить реальный `POST /requests` и сохраненные поля в Mock API |
| Тесты Retry не проходят | Проверить, что при 503 есть повтор, а при 400 его нет, и интервалы не меньше 400 мс |
| Все тесты падают с 404 | Проверить путь `support-request`, метод POST, публикацию и единственность опубликованного workflow |

## 7. Требования к воспроизводимости

- Тесты запускаются **последовательно**. Параллельный запуск и ручное взаимодействие с Mock API во время проверки не поддерживаются.
- Тесты рассчитаны на исходные `mock-api/`, `compose.yaml` и `tests/`; изменять их при выполнении ДЗ нельзя.
- Код завершения `0` означает прохождение всех тестов выбранного режима, `1` - что есть непройденные проверки, `2` - недоступность Mock API или ошибку предварительной проверки.
- Файлы отчетов перезаписываются при следующем запуске; при необходимости сохраните их отдельно.
- Для проверки уровня Э демонстрация дополнительных заданий должна войти в обязательный видеоотчет.
