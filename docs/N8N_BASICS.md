# Практикум: как читать и собирать workflow в n8n

**Цель:** за 30–50 минут познакомиться с редактором n8n, передачей JSON между узлами и обращением к HTTP API. Этот практикум **не является решением основной задачи**.

## Перед началом

1. Выполните `docker compose up -d` из корня проекта.
2. Откройте `http://localhost:5678`, завершите настройку локального аккаунта, если это первый запуск.
3. Импортируйте `workflows/tutorial-basics.json` через меню импорта файла.
4. Откройте схему. На полотне расположены **Sticky Notes** с пояснениями. Выполните пример кнопкой **Execute workflow**.

В разных версиях n8n названия пунктов интерфейса могут немного отличаться. Используйте закрепленную версию из `.env.example`.

## 1. Из чего состоит workflow

- **Node** — действие: создать поля, проверить условие, выполнить HTTP-запрос.
- **Connection** — направление передачи данных между узлами.
- **Execution** — отдельный запуск схемы с конкретными входными данными.
- **Manual Trigger** — ручной запуск учебного примера.
- **Webhook** — прием HTTP-запросов от внешнего клиента (понадобится в основном задании).
- **Sticky Note** — пояснение на схеме, которое не выполняется.

После запуска откройте любой узел и сравните вкладки **Input** и **Output**. Чаще всего данные проходят как объекты JSON; следующий узел получает результат предыдущего, а не автоматически все значения со всей схемы.

## 2. Эксперимент 1: редактирование данных

Откройте узел `Example input` (**Edit Fields**), найдите значения `requestId`, `userId` и `priority`. Это исходные тестовые данные для примера. Запустите workflow и убедитесь, что они видны в Output.

**Задание:** поменяйте `priority` на `medium`, повторите запуск. Сравните выходы узла `Is high priority?` и поле `exampleBranch` на выбранной ветке.

**Ожидаемый результат:** при `high` выполняется ветка true, при `medium` — ветка false. Остальные поля остаются доступными, так как в демонстрационных Edit Fields включено сохранение входных данных.

## 3. Эксперимент 2: expressions

В узле `Get demo user` URL строится выражением:

```javascript
{{ 'http://mock-api:8080/users/' + $json.userId }}
```

`$json.userId` означает «возьми поле `userId` из текущего входного элемента». Эта запись не хранит значение `451` жестко в узле HTTP Request: источник ID — предыдущие шаги.

**Задание:** установите `userId = 452` в `Example input`, запустите workflow и посмотрите фактический URL HTTP Request и его Output.

**Ожидаемый результат:** получен пользователь `Мария Смирнова` из отдела `Finance`.

**Подумайте:** почему `http://127.0.0.1:8080/users/452` работает на вашем компьютере, но в HTTP Request внутри контейнера правильнее использовать `http://mock-api:8080/users/452`?

## 4. Эксперимент 3: If и Switch — не одно и то же

**If** имеет две ветви — условие true или false. В примере он проверяет, равно ли `priority` значению `high`.

**Switch** выбирает из нескольких направлений. В примере `Route by department` проверяет `department` **из ответа Mock API**: `IT`, `Finance`, иначе fallback `Other`.

Выполните подряд:

| `userId` в `Example input` | Ожидаемая ветка `Switch` |
|---:|---|
| 451 | IT |
| 452 | Finance |
| 453 | Other (fallback, так как отдел Security) |

Почему узел `Route by department` работает с полем `department`, хотя в исходном `Example input` его не было? Ответ: это поле добавилось не в исходный JSON, а пришло **в ответе HTTP Request**.

## 5. Эксперимент 4: не теряйте входные данные

Сравните:

1. Output узла `Example input` — поля исходного обращения.
2. Output узла `Get demo user` — поля пользователя, которые вернул HTTP API.

В реальном workflow может понадобиться одновременно использовать обе группы полей. Поэтому при разработке основного задания продумайте, **откуда брать исходный `requestId` и `description` после HTTP-запроса**. Никакого готового решения этот практикум не дает: исследуйте доступные способы передачи/обращения к данным.

## 6. Как исследовать ошибку

Поменяйте `userId` на `9999` и запустите пример. Mock API вернет `404`. Откройте запись выполнения и найдите узел, на котором прервался процесс.

После этого восстановите `userId = 451`. В основном задании ошибки должны не просто прерывать workflow, а приводить к **оговоренному HTTP-ответу**. Для этого вам предстоит самостоятельно изучить настройки обработки ошибок узлов и `Respond to Webhook`.

## 7. Мини-контроль перед основным заданием

Вы готовы продолжать, если можете ответить на вопросы:

1. Что отображают Input и Output узла?
2. Почему выражение с `$json` зависит от входных данных?
3. Чем две ветки If отличаются от правил Switch?
4. Чем `localhost` внутри контейнера отличается от адреса другого сервиса в Compose?
5. Почему после HTTP Request нельзя предполагать, что весь исходный JSON по-прежнему в `$json`?
6. Чем тестовый адрес Webhook отличается от Production URL?
