# Как сдать лабораторную работу

Сдача состоит из **экспортированного workflow, письменного отчета и обязательного видеоотчета**. Все это связывается в одном Pull Request (PR) в репозиторий эксперта.

> Пока официальный GitHub-адрес задания не опубликован, в инструкциях ниже используются обозначения `<URL-РЕПОЗИТОРИЯ>` и `<ВАШ-FORK>`. После публикации преподавателем/экспертом замените их реальными ссылками. Не создавайте PR в чужой репозиторий по случайному примеру.

| Артефакт | Где находится |
|---|---|
| Основное решение (JSON) | `submissions/support-request-workflow.json` |
| Отчет | `REPORT.md` |
| Видеоотчет | Ссылка в `REPORT.md` и в описании PR |
| Результаты базовых тестов | `REPORT.md`, при необходимости кратко в PR |
| Результаты экспертных тестов (если Э) | `REPORT.md` и видео |

## 1. Подготовьте свою копию репозитория

1. Откройте GitHub-репозиторий задания по ссылке от преподавателя.
2. Создайте fork в свой аккаунт GitHub.
3. Клонируйте свой fork любым способом, например через **Code → HTTPS → Copy URL** и `git clone <ВАШ-FORK>`.
4. Создайте отдельную ветку, например:

```shell
git switch -c solution/n8n-lab
```

Если fork или PR в условиях конкретной группы не используются, преподаватель должен указать альтернативный порядок передачи архива. **По умолчанию сдаем через PR**.

## 2. Выполните задание и проверьте работу

Прочитайте [ASSIGNMENT.md](ASSIGNMENT.md), создайте и **опубликуйте** в n8n собственный workflow. Запустите:

```shell
python tests/run_tests.py --mode base
```

Для уровня Э дополнительно:

```shell
python tests/run_tests.py --mode expert
```

Тестовый раннер создает `reports/latest-results.md` и `reports/latest-results.json`. Они **не включены в Git**: основные числа и ошибки перенесите в `REPORT.md`. Непройденные проверки нужно перечислить, не скрывая их.

## 3. Экспортируйте workflow

1. Откройте **основной** workflow в редакторе n8n (не обучающий пример).
2. Сохраните последние изменения и убедитесь, что они проверены.
3. В меню workflow выберите экспорт/скачивание JSON (название пункта зависит от версии интерфейса).
4. Сохраните файл как `submissions/support-request-workflow.json`.
5. Перед сдачей проверьте, что файл действительно содержит ваши узлы и может импортироваться обратно в n8n.

**Предупреждение:** экспорт может содержать конфигурацию узлов и ссылки на учетные данные. В работе не нужны реальные токены. Не добавляйте в JSON, README, отчет или PR пароли, токены, cookies и персональные данные.

## 4. Заполните письменный отчет

Откройте [`REPORT.md`](../REPORT.md) и внесите реальные результаты:

- какие части выполнены, какие нет;
- функциональная оценка `X/60`, перечень непройденных ID;
- итог экспертных тестов (если выполнялись);
- причины основных технических решений;
- возникшие проблемы и ограничения;
- фактически потраченное время, **включая запись видео**;
- ссылку на видео и его длительность.

Отчет должен соответствовать **той же версии workflow**, которую вы прикладываете.

## 5. Запишите обязательный видеоотчет

Рекомендуемая длительность — **около 4 минут**, допустимый ориентир **3–6 минут**. Запишите экран с кратким голосовым комментарием либо понятными текстовыми пояснениями (если формат согласован с экспертом). Важнее содержание, чем монтаж.

| Примерное время | Что показать | Баллы |
|---|---|---:|
| 0:00–0:40 | Общая структура и смысл основных веток | 4 |
| 0:40–1:40 | Успешное обращение: вход, выполнение, реальная регистрация | 6 |
| 1:40–2:20 | Некорректное обращение или сбой API | 5 |
| 2:20–3:20 | Почему выбраны такие узлы, как передаются данные | 6 |
| 3:20–4:00 | Команда тестов и интерпретация результата | 4 |

Если заявляете Э, дополнительно продемонстрируйте логику Retry и отсутствие повторной регистрации; ролик может быть ближе к верхней границе. Для подтверждения регистрации можно показать запись в `GET /__test__/records`, но не нужно объяснять внутреннюю реализацию Mock API.

Поместите видео в хранилище или на видеохостинг с **доступом по ссылке**, вставьте URL в `REPORT.md` и описание PR. Обязательно откройте ссылку в приватном окне браузера, чтобы убедиться, что эксперт сможет просмотреть запись. **Если видео отсутствует или недоступно, работа возвращается как неполная и итоговый уровень не выставляется**, независимо от тестов.

## 6. Создайте Pull Request

Убедитесь, что изменяются только файлы сдачи. Базовый вариант:

```shell
git status --short
git add submissions/support-request-workflow.json REPORT.md
git commit -m "Complete n8n support request workflow"
git push -u origin solution/n8n-lab
```

На GitHub своего fork создайте PR из `solution/n8n-lab` в `main` **исходного репозитория задания**. Заполните шаблон PR. Добавьте ссылку на видео и краткий результат тестов. Если изменяли другие файлы для реализации, опишите необходимость изменений; изменять `mock-api/` и исходные `tests/` ради обхода проверок **запрещено**.

## 7. Если эксперт попросил исправления

Внесите изменения в workflow, заново экспортируйте JSON, повторите проверки и при необходимости перезапишите видео. Обновите `REPORT.md`, сохраните коммит и отправьте изменения в ту же ветку: PR обновится автоматически.

## Самопроверка перед сдачей

- [ ] В PR есть **основной** workflow, а не tutorial или пустая заготовка.
- [ ] JSON можно импортировать в n8n, webhook имеет путь `support-request`.
- [ ] `REPORT.md` заполнен по реальным результатам, известные ошибки перечислены.
- [ ] Видео доступно без дополнительного одобрения и показывает результаты тестов.
- [ ] Видео и отчет соответствуют коду в PR.
- [ ] В PR нет эталонного решения, ключей, данных n8n и файлов из локального Docker volume.
- [ ] Для Э: оба дополнительных задания и все 8 экспертных проверок.
