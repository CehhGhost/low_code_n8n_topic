# Этап 5: проверка функционального тестового раннера

## Проверка на опубликованном эталонном workflow

1. Обновите файлы проекта из архива этапа 5. Образ n8n менять не нужно.
2. Выполните `docker compose up -d` (если окружение уже запущено, это безопасно).
3. Откройте n8n и **опубликуйте `reference-baseline`**, отключив студенческую заготовку.
4. Запустите **из корня студенческого репозитория**:

```powershell
python tests/run_tests.py --mode base
```

5. Ожидаемая цель - **18/18 PASS, 60/60 функциональных баллов**. Это контрольная цель, пока не подтвержденная запуском на твоем локальном n8n (Python-симулятор проходит все 18 случаев).
6. Откройте `reports/latest-results.md` и `reports/latest-results.json` - результат должен совпадать с выводом в консоли.

После успешной проверки базового эталона *по желанию* выполните:

```powershell
python tests/run_tests.py --mode expert
```

Так как базовый эталон **специально не содержит** Retry и защиты от дубликатов, большинство экспертных проверок должны быть провалены. Это ожидаемо и не является ошибкой раннера.

## Контроль самих тестов без Docker

Из корня **студенческого** проекта:

```powershell
python -m unittest discover -s tests -p 'test_*.py' -v
```

Для преподавателя дополнительно есть изолированное интеграционное тестирование раннера из архива эксперта: оно поднимает на свободных localhost-портах Mock API и маленький имитатор Webhook (не n8n), проверяет полный проход 60/60 и 8/8 и отрицательные сценарии.

## Если тест падает

1. Сохраните строку `FAIL` и запись из `reports/latest-results.md`.
2. Откройте `Executions` в n8n, найдите соответствующий запуск.
3. Убедитесь, что HTTP Request обращается к `http://mock-api:8080`, а не к `localhost:8080` из контейнера.
4. Пришлите ID первого непройденного теста, его сообщение и, если нужно, скриншот узлов n8n.

**Не запускайте два набора тестов одновременно:** каждый сценарий очищает Mock API.
