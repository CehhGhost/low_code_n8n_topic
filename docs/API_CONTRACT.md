# Контракт Mock API

> Статус: проектная спецификация, версия 1.0. Фактическая реализация и тестирование сервера будут выполнены на следующем техническом этапе. Этот документ описывает **целевое** поведение API, а не уже запущенный сервис.

## 1. Назначение и адреса

Mock API имитирует два внешних сервиса: справочник пользователей и регистрацию обращений. API уже реализован авторами задания; писать свой сервер студенту не нужно.

| Откуда выполняется запрос | Адрес Mock API |
|---|---|
| Из workflow в контейнере n8n | `http://mock-api:8080` |
| С компьютера студента / из тестового скрипта | `http://127.0.0.1:8080` |

Адрес n8n из браузера и для тестов: `http://localhost:5678`. Путь рабочего Webhook: `POST /webhook/support-request`. Для автоматических проверок workflow нужно активировать (опубликовать) в n8n: тестовый путь `/webhook-test/...` не используется.

Все JSON-ответы имеют заголовок `Content-Type: application/json`. Стандартные успешные ответы возвращаются с кодом 200 или 201. В тестовых запросах нет аутентификации, поскольку окружение локальное. Порт Mock API в Docker Compose привязывается только к `127.0.0.1` хоста.

## 2. Справочник пользователей

### GET /users/{userId}

**Успех:** `200 OK`, ответ:

```json
{
  "id": 451,
  "name": "Иван Иванов",
  "department": "IT",
  "email": "ivan@example.com"
}
```

Тестовые пользователи (значения фиксированы):

| ID | name | department | email |
|---|---|---|---|
| `451` | Иван Иванов | IT | ivan@example.com |
| `452` | Мария Смирнова | Finance | maria@example.com |
| `453` | Петр Орлов | Security | petr@example.com |

Другие ID (включая `9999`) отсутствуют, поэтому ответ: `404 Not Found`.

```json
{"error":{"code":"USER_NOT_FOUND","message":"Пользователь не найден"}}
```

Ошибки HTTP 503 и другие тестовые статусы генерируются **служебным управлением сбоями** (раздел 5), а не зашитыми «специальными» userId.

## 3. Регистрация обращений

### POST /requests

**Тело запроса**, которое должен сформировать workflow:

```json
{
  "requestId": "REQ-1024",
  "userId": 451,
  "userName": "Иван Иванов",
  "department": "IT",
  "type": "technical",
  "priority": "high",
  "description": "Не удается авторизоваться в системе",
  "assignedGroup": "Technical Support",
  "slaHours": 1,
  "status": "registered"
}
```

Mock API проверяет обязательные поля и типы. При некорректном теле возвращает `400 Bad Request` с кодом `INVALID_REQUEST`. В обычном случае сохраняет новую запись и возвращает:

**`201 Created`**

```json
{
  "recordId": "rec-000001",
  "requestId": "REQ-1024",
  "status": "registered"
}
```

`recordId` - внутренний уникальный ID записи, назначаемый сервером; значение выше приведено для примера, тесты **не сравнивают его с фиксированной строкой**.

**Принципиальное решение:** Mock API **не проверяет уникальность `requestId`**. Каждый успешный `POST /requests` создает новую запись, даже если `requestId` уже встречался. Иначе экспертная задача на защиту от дублирования решалась бы самой заглушкой, а не workflow студента.

### GET /requests/{requestId}

Возвращает **первую зарегистрированную запись** с данным `requestId` (`200 OK`) либо `404 Not Found` с `REQUEST_NOT_FOUND`. Запись содержит все поля тела `POST /requests` и дополнительное поле `recordId`. Этот endpoint можно использовать в экспертной задаче для проверки существования обращения.

Если по одному `requestId` было сохранено несколько записей, метод все равно возвращает первую. Для выявления дубликатов тесты используют служебный метод `/__test__/records`.

## 4. Контракт webhook студента

### POST /webhook/support-request

**Входной JSON:**

```json
{
  "requestId": "REQ-1024",
  "userId": 451,
  "type": "technical",
  "priority": "high",
  "description": "Не удается авторизоваться в системе"
}
```

**Правила валидации:**

- Тело должно быть JSON-объектом (не массивом и не скалярным значением).
- `requestId`, `type`, `description` - строки, содержащие минимум один непробельный символ.
- `userId` - строго положительное целое число (не `true`, не строка и не дробное число).
- `priority` - строго `high`, `medium` или `low` (регистр учитывается).
- Дополнительные поля допускаются и игнорируются.
- Значения строк сохраняются в исходном виде; пробелы учитываются только при проверке на пустоту.

**Маршрутизация:** `technical` → `Technical Support`, `billing` → `Finance`, `access` → `Security`, любой иной непустой `type` → `General Support`.

**SLA:** `high` → 1 час, `medium` → 4 часа, `low` → 24 часа.

**Ответ при успехе:** `201 Created` и JSON:

```json
{
  "requestId": "REQ-1024",
  "status": "registered",
  "assignedGroup": "Technical Support",
  "slaHours": 1,
  "userName": "Иван Иванов"
}
```

Результат должен появиться **после подтвержденной успешной регистрации** через `POST /requests`.

**Единый формат ошибок:**

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Некорректные данные обращения"
  }
}
```

| Условие | HTTP | `error.code` | Ограничение |
|---|---:|---|---|
| Ошибка входных данных | 400 | `VALIDATION_ERROR` | Не вызывать `GET /users` и `POST /requests` |
| Пользователь не найден (`GET /users` вернул 404) | 404 | `USER_NOT_FOUND` | Не вызывать `POST /requests` |
| Иная ошибка чтения пользователя (`5xx`) | 502 | `UPSTREAM_ERROR` | Не вызывать `POST /requests` |
| Ошибка регистрации обращения (`4xx/5xx`) | 502 | `UPSTREAM_ERROR` | Не возвращать ложный успех |

Поле `message` должно быть непустой строкой; точная формулировка не проверяется. Для базового задания достаточно корректно вернуть ошибку при постоянно недоступном внешнем API. Механизм Retry в базовой части не требуется.

## 5. Служебное API для автоматических тестов

**Важно:** префикс `/__test__` используется исключительно тестовым скриптом; студент не должен вызывать эти методы из своего workflow.

### POST /__test__/reset

Вход: `{}`. Очищает записи обращений, журнал вызовов и заданные сценарии ошибок; тестовые пользователи восстанавливаются. Ответ `200`:

```json
{"status":"reset"}
```

### POST /__test__/failures

Настраивает последовательность искусственных ошибок для точного сочетания HTTP-метода и пути:

```json
{
  "method": "POST",
  "path": "/requests",
  "statuses": [503, 503],
  "repeatLast": false
}
```

Каждый подходящий вызов потребляет один статус из `statuses`. Если он не 2xx, Mock API возвращает указанный код с телом `{"error":{"code":"SIMULATED_FAILURE","message":"..."}}` **без выполнения операции и без сохранения записи**.

Если `statuses` закончились:
- при `repeatLast: false` (по умолчанию) выполняется обычная обработка запроса: в данном примере третий `POST /requests` вернет `201 Created`;
- при `repeatLast: true` последняя ошибка повторяется при каждом следующем вызове до сброса состояния.

Для постоянной ошибки `400` использовать `{"method":"POST","path":"/requests","statuses":[400],"repeatLast":true}`.

`statuses` содержит только значения ошибок `400`–`599`. Служебная настройка заменяет собой встроенные «магические» идентификаторы для эмуляции ошибок.

### GET /__test__/calls

Ответ `200`, пример:

```json
{
  "calls": [
    {"method":"GET","path":"/users/451","status":200,"timestampMs":1792400000000},
    {"method":"POST","path":"/requests","status":503,"timestampMs":1792400000510},
    {"method":"POST","path":"/requests","status":201,"timestampMs":1792400001020}
  ]
}
```

Записываются вызовы **основных** API (`/users/...`, `/requests...`), но не обращения к `/__test__/...` или `/health`. `timestampMs` фиксирует момент приема запроса (Unix time, миллисекунды). Тесты используют журнал для проверки количества повторов и времени между ними.

### GET /__test__/records

Ответ `200`:

```json
{"records":[{"recordId":"rec-000001","requestId":"REQ-1024","userId":451,"status":"registered"}]}
```

Возвращает полный список фактически сохраненных записей, включая дубликаты. В реальном API такой метод не требуется, но здесь он служит источником проверяемых свидетельств.

## 6. Ограничения и договоренности

- Docker Compose содержит n8n и Mock API в одной сети. Отдельные платные ключи и аккаунты не нужны.
- Тесты последовательно сбрасывают состояние перед каждым независимым сценарием; параллельный запуск тестов не поддерживается.
- Логика обработки входных данных находится в n8n, а не в Mock API.
- Студенческие автотесты не принимают за решение простую выдачу заранее заготовленного HTTP-ответа: проверяют реальные вызовы и сохраненные записи.
- В экспертной части повторная регистрация одного `requestId` предотвращается **для последовательных запросов**; гонки между одновременными Webhook-вызовами не входят в требования.
- Реализация сервера Mock API и тестового раннера должна строго следовать этому контракту; при расхождении корректируем проект до публикации задания.
