# Тестовые сценарии и начисление баллов

> Статус: согласованный проект проверок, версия 1.0. Ниже описана **будущая** автоматизированная проверка; сами исполняемые тесты будут написаны на этапе реализации. Этот документ входит в публичную часть задания.

## 1. Принципы проверки

- Базовая часть: **60 баллов** за 18 функциональных тест-групп. Баллы за видео, письменный отчет и оформление workflow оцениваются отдельно по `GRADING.md`.
- Каждый тест-группа получает **фиксированное** число баллов только тогда, когда все проверки в ней успешны. Частичных и экспертных «на глаз» баллов за одну тест-группу нет.
- Перед независимым сценарием тестовый раннер делает `POST /__test__/reset`, при необходимости настраивает `POST /__test__/failures`, затем отправляет запрос на рабочий Webhook.
- Оцениваются HTTP-коды, структура JSON, фактические записи и вызовы Mock API. Внутренняя расстановка узлов n8n не проверяется автотестами.
- Проходящие тесты не отменяют требования иметь читаемую схему и видео. Невозможность воспроизвести запуск на согласованном окружении требует исправления сдачи.

## 3. Дополнительные задания - условия уровня Э

Для экспертного уровня требуется выполнить **все** тесты ниже, а также соответствовать уровню **П** по основной шкале. Дополнительные тесты не компенсируют дефекты базовой части.

### EXP-R. Ограниченный Retry

Студент реализует Retry для `POST /requests` при HTTP 503. Для получения экспертного уровня должны выполняться следующие условия:

- Не более **3 попыток всего**, включая первичный вызов (то есть максимум 2 повтора).
- Задержка **не менее 0,4 секунды** между попытками при 503. Время сравнивается по журналу вызовов. Реализация может использовать фиксированную задержку; exponential backoff не требуется.
- При `400` повторов нет. При исчерпании попыток возвращается `502 UPSTREAM_ERROR`.
- Повторы `GET /users` для уровня Э не требуются; проверяется именно `POST /requests`.

| ID | Критерий | Ожидаемый результат |
|---|---|---|
| `EXP-R01` | 503, затем обычный успех | `201`, ровно 2 вызова `POST /requests`, 1 сохраненная запись |
| `EXP-R02` | 503, 503, затем обычный успех | `201`, ровно 3 вызова `POST /requests`, 1 сохраненная запись |
| `EXP-R03` | Постоянный 503 | `502`, ровно 3 попытки, 0 записей |
| `EXP-R04` | Постоянный 400 | `502`, ровно 1 попытка, 0 записей |
| `EXP-R05` | Временные интервалы | Между повторными вызовами `POST /requests` при 503 не менее 0,4 секунды |

### EXP-D. Идемпотентность последовательных запросов

Mock API **не предотвращает** дубликаты. Защиту реализует workflow, например используя доступное API для проверки существующей записи. Способ реализации не предписывается.

| ID | Критерий | Ожидаемый результат |
|---|---|---|
| `EXP-D01` | Первый запрос с новым `requestId` | `201`, одна регистрация |
| `EXP-D02` | Такой же запрос с тем же `requestId` после успешного первого | `200`, `{"requestId":"...","status":"already_registered"}`, новых `POST /requests` нет, всего одна запись |
| `EXP-D03` | Новый `requestId` после дубликата | Регистрируется независимо, корректный `201`, всего две записи с разными `requestId` |

**Важно:** задача ограничена последовательными повторами, без параллельных запросов и требования атомарной exactly-once обработки в распределенной системе. В тестах экспертной части также проверяется корректная работа базовых сценариев.

## 4. Примеры ручной проверки

После старта окружения и активации рабочего webhook:

```bash
curl -i -X POST http://localhost:5678/webhook/support-request \
  -H 'Content-Type: application/json' \
  -d '{"requestId":"REQ-1024","userId":451,"type":"technical","priority":"high","description":"Не удается авторизоваться"}'
```

Ручной просмотр регистраций:

```bash
curl http://127.0.0.1:8080/__test__/records
```

Скрипты автопроверки будут предоставлены в проекте на следующих этапах. Команды выше - **запланированный интерфейс** еще не созданного окружения.

## 5. Важные правила оценивания

- Видеоролик **обязателен** даже при успешном прохождении всех тестов; требования и 25 баллов за содержание см. `GRADING.md`.
- Выполнение одной дополнительной задачи без второй **не дает уровень Э**.
- Дополнительное задание не требует использования конкретного n8n-узла или написания кода: оценивается поведение.
- Неизменяемые элементы тестовой инфраструктуры (Mock API, служебные endpoints и сами проверочные сценарии) считаются частью условий; их изменение не засчитывается как решение.
