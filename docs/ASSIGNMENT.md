# Практическое задание: Low-code автоматизация обработки обращений в n8n

**Длительность:** ориентировочно 7-8 часов для базового задания и еще 2-3 часа для дополнений.  
**Подготовка:** по сути ничего особо не требуется, если у тебя не было до этого опыта работы с n8n, то не страшно, данная работа как раз направлена на ознакомление с ними (если все равно что-то непонятно, то напиши нам, мы подскажем)  
**Результат:** работающий опубликованный workflow, экспортированный JSON, заполненный `REPORT.md`, видеоотчет и Pull Request.

## 1. Зачем это задание

Не всегда для решения некоторых задач необходимо писать отдельный backend сервис, иногда можно обойтись и Low-code решениями, одним из инструментов для создания которых является n8n. Тебе предлагается познакомиться с ним поближе, на примере условной ситуации, когда компании получают обращения через разные каналы и передают их между системами. Для решения задачи достаточно визуального workflow, который принимает событие, проверяет данные, обращается к API и возвращает ответ, что тебе и предстоит реиализовать.

Не придется разрабатывать отдельный backend сервис: **Mock API, Docker Compose и автотесты уже готовы**. Твоя задача - реализовать обработку в редакторе n8n и проверить ее работу.

## 2. Начальное состояние

В репозитории есть:

- `compose.yaml` — локальные n8n и Mock API;
- `workflows/tutorial-basics.json`, `workflows/tutorial-items-loops.json`, `workflows/tutorial-webhook.json` - три небольших учебных примера, чтобы ознакомиться с основами.
- `workflows/student-starter.json` - отдельная заготовка c `Webhook` для итогового ДЗ.
- `docs/API_CONTRACT.md` - точные требования к входу, выходу и API, которые помогут пройти тесты.
- `tests/run_tests.py` - автоматические функциональные проверки (не пытайся подстроиться под них, в видеоролике все равно это будет заметно =) ).

## 3. Этап 0. Запустить окружение и изучить примеры (около 1-1,5 часа)

1. Подготовь Docker и Python 3.10+. Подробности в [SETUP.md](SETUP.md).
2. Запусти `docker compose up -d`. Проверь `http://localhost:5678` и `http://127.0.0.1:8080/health`.
3. По очереди импортируй в n8n три учебных workflow из `workflows/tutorial-*.json`.
4. Пройди [N8N_BASICS.md](N8N_BASICS.md): триггеры, Input/Output, expressions, предыдущие узлы, If/Switch, HTTP Request, несколько items и циклы.
5. Импортируй `workflows/student-starter.json` как **отдельный workflow** и изучи Webhook / Respond to Webhook.

## 4. Этап 1. Прием и проверка входных данных

Настрой `POST /webhook/support-request` для приема JSON следующего вида:

```json
{
  "requestId": "REQ-1024",
  "userId": 451,
  "type": "technical",
  "priority": "high",
  "description": "Не работает авторизация"
}
```

Реализуй валидацию:

- `requestId`, `type`, `description` — непустые строки (строка из пробелов недопустима).
- `userId` - положительное целое число, не логическое значение и не строка.
- `priority` - одно из `high`, `medium`, `low` (строго с учетом регистра).
- все обязательные поля должны присутствовать, дополнительные поля допустимы.

При ошибке входных данных возвращай **HTTP 400** и JSON с `error.code = "VALIDATION_ERROR"`. Ни один внешний API при этом вызывать **нельзя**, все должно заканчиваться на возврате ошибки. Полная таблица в [API_CONTRACT.md](API_CONTRACT.md).

**Проверка этапа:** корректный JSON проходит дальше, некорректный завершается ошибкой без побочных эффектов.

## 5. Этап 2. Получить пользователя и назначить исполнителя

После валидации получи пользователя из `GET http://mock-api:8080/users/{userId}`. Доступны ID `451`, `452`, `453`. Для остальных ID, например "9999" сервис вернет `404`: Webhook должен ответить **HTTP 404** с `error.code = "USER_NOT_FOUND"` и **не** регистрировать обращение.

Определи ответственную группу и SLA:

| `type` | `assignedGroup` |
|---|---|
| `technical` | `Technical Support` |
| `billing` | `Finance` |
| `access` | `Security` |
| Любой другой непустой | `General Support` |

| `priority` | `slaHours` (число) |
|---|---:|
| `high` | 1 |
| `medium` | 4 |
| `low` | 24 |

Используй стандартные возможности n8n или собственную логику: **нет четкого единственно правильного решения**, проверяется результат и логика решения, которая будет отражена в отчете и видео. Убедись, что после HTTP Request не потерялись поля исходного обращения.

## 6. Этап 3. Зарегистрировать обращение и вернуть ответ

Сформируй объект для `POST http://mock-api:8080/requests`, включив:

`requestId`, `userId`, `userName`, `department`, `type`, `priority`, `description`, `assignedGroup`, `slaHours`, `status: "registered"`.

Только **после успешной регистрации** верни **HTTP 201**:

```json
{
  "requestId": "REQ-1024",
  "status": "registered",
  "assignedGroup": "Technical Support",
  "slaHours": 1,
  "userName": "Иван Иванов"
}
```

Результат должен **фактически присутствовать** в Mock API. Тесты проверяют сохраненные данные, поэтому простая выдача заранее заготовленного ответа не подходит.

Для двух **разных** обращений данные не должны смешиваться.

## 7. Этап 4. Ошибки внешних сервисов

Настрой корректное поведение в следующих случаях:

- `GET /users/{id}` вернул `404` - Webhook отвечает `404 USER_NOT_FOUND`.
- получение пользователя вернуло `5xx` - `502 UPSTREAM_ERROR`.
- регистрация вернула `4xx/5xx` - `502 UPSTREAM_ERROR`.

Для ошибок используется единая структура:

```json
{
  "error": {
    "code": "UPSTREAM_ERROR",
    "message": "Не удалось выполнить запрос к внешнему сервису"
  }
}
```

`message` должна быть непустой строкой, точный текст не оценивается. **Для базового уровня пока достаточно просто вернуть ошибку**

## 8. Этап 5. Самопроверка и оформление (обязательно)

1. Сохрани и **опубликуй** workflow.
2. Не допускайте публикации двух workflow с одинаковым путем Webhook (просто возьми за правило - один опубликованный workflow за раз).
3. Из корня репозитория выполни:

```shell
python tests/run_tests.py --mode base
```

4. Посмотри `reports/latest-results.md`. Всего **18 групп**, суммарно **60 баллов** за функциональность.
5. Исправь ошибки если таковы есть.
6. Переименуй узлы так, чтобы было понятно их назначение, оставь пояснения к нетривиальной логике. В задании аккуратное оформление и оптимальность решения также оцениваются.
7. Экспортируй основной workflow в `submissions/support-request-workflow.json` (или продолжи работу в шаблоне, но отрази это в отчете письменном).

## 9. Дополнительная часть для уровня Э (до 2–3 часов)

Выполняется **после** базовой части. В отличие от учебного практикума, здесь не дается пошагового алгоритма и не предписываются конкретные узлы. Ненобходимо самостоятельно исследовать возможности n8n и выбирать реализацию.

### Задание Э-1. Управляемые повторные попытки при сбое

Дополни **регистрацию** обращения так, чтобы при временном `HTTP 503` операция повторялась. Ограничения:

- **не более 3 вызовов всего** (исходный + до 2 повторов).
- между повторными запросами после `503` - задержка **не менее 0,4 секунды**.
- при `400` повторно обращаться **нельзя**.
- если все попытки завершились `503`, Webhook возвращает `502 UPSTREAM_ERROR`.
- если сервис восстановился на второй или третьей попытке, регистрация завершается `201` и появляется ровно одна запись.

### Задание Э-2. Защита от повторной регистрации

Два последовательно поступивших обращения с одним и тем же `requestId` **не должны создавать две записи**. Для второго запроса нужен `HTTP 200`:

```json
{"requestId":"REQ-1024","status":"already_registered"}
```

Следующее обращение с **другим** `requestId` должно обрабатываться как новое. Гонки между одновременными запросами не проверяются (предположим, что все запросы выполняются последовательно). Mock API сам **не** предотвращает дубликаты, это нужно реализовать в workflow.

Проверка дополнений:

```shell
python tests/run_tests.py --mode expert
```

Все восемь экспертных проверок необходимы для уровня Э. Дополнительная часть будет учитываться только в случае выполнения базового задания.
