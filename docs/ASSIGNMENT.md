# Практическое задание: Low-code автоматизация обработки обращений в n8n

**Длительность:** ориентировочно 7–8 часов для базового задания и еще 2–3 часа для дополнений. **Общий лимит — 12 астрономических часов, включая отчет и видео.**  
**Подготовка:** базовое понимание HTTP и JSON; опыт с n8n, Java, Python и базами данных не требуется.  
**Результат:** работающий опубликованный workflow, экспортированный JSON, заполненный `REPORT.md`, видеоотчет и Pull Request.

## 1. Зачем это задание

Компании получают обращения через разные каналы и передают их между системами. Иногда для автоматизации этого процесса не нужен отдельный backend-сервис: достаточно визуального workflow, который принимает событие, проверяет данные, обращается к API и возвращает ответ. В этой работе вы познакомитесь с **n8n** — платформой для создания таких автоматизаций.

Вы не разрабатываете API-сервер: **Mock API, Docker Compose и автотесты уже готовы**. Ваша задача — реализовать обработку в редакторе n8n и проверить ее работу.

## 2. Начальное состояние

В репозитории есть:

- `compose.yaml` — локальные n8n и Mock API;
- `workflows/tutorial-basics.json`, `workflows/tutorial-items-loops.json`, `workflows/tutorial-webhook.json` — три небольших учебных примера, не являющихся решением;
- `workflows/student-starter.json` — отдельная заготовка c `Webhook` и ответом `TODO`;
- `docs/API_CONTRACT.md` — точные требования к входу, выходу и API;
- `tests/run_tests.py` — автоматические функциональные проверки.

**Важно:** учебный пример и студенческая заготовка выполняют разные задачи. Первую используйте для знакомства с интерфейсом, вторую изменяйте для сдачи.

## 3. Этап 0. Запустить окружение и изучить примеры (около 1–1,5 часа)

1. Подготовьте Docker и Python 3.10+; подробности в [SETUP.md](SETUP.md).
2. Запустите `docker compose up -d`. Проверьте `http://localhost:5678` и `http://127.0.0.1:8080/health`.
3. По очереди импортируйте в n8n три учебных workflow из `workflows/tutorial-*.json`.
4. Пройдите [N8N_BASICS.md](N8N_BASICS.md): триггеры, Input/Output, expressions, предыдущие узлы, If/Switch, HTTP Request, несколько items и циклы.
5. Импортируйте `workflows/student-starter.json` как **отдельный workflow** и изучите Webhook / Respond to Webhook.

**Проверка этапа:** вы можете объяснить, как данные проходят между узлами и почему URL Mock API внутри Docker выглядит как `http://mock-api:8080`.

## 4. Этап 1. Прием и проверка входных данных

Настройте `POST /webhook/support-request` для приема JSON следующего вида:

```json
{
  "requestId": "REQ-1024",
  "userId": 451,
  "type": "technical",
  "priority": "high",
  "description": "Не работает авторизация"
}
```

Реализуйте валидацию:

- `requestId`, `type`, `description` — непустые строки (строка из пробелов недопустима);
- `userId` — положительное целое число, не логическое значение и не строка;
- `priority` — одно из `high`, `medium`, `low` (строго с учетом регистра);
- все обязательные поля должны присутствовать; дополнительные поля допустимы.

При ошибке входных данных верните **HTTP 400** и JSON с `error.code = "VALIDATION_ERROR"`. Ни один внешний API при этом вызывать **нельзя**. Полная таблица — в [API_CONTRACT.md](API_CONTRACT.md).

**Проверка этапа:** корректный JSON проходит дальше, некорректный завершается ошибкой без побочных эффектов.

## 5. Этап 2. Получить пользователя и назначить исполнителя

После валидации получите пользователя из `GET http://mock-api:8080/users/{userId}`. Доступны ID `451`, `452`, `453`. Для ID `9999` сервис вернет `404`: ваш Webhook должен ответить **HTTP 404** с `error.code = "USER_NOT_FOUND"` и **не** регистрировать обращение.

Определите ответственную группу и SLA:

| `type` | `assignedGroup` |
|---|---|
| `technical` | `Technical Support` |
| `billing` | `Finance` |
| `access` | `Security` |
| Любой другой непустой | `General Support` |

| `priority` | `slaHours` (число) |
|---|---:|
| `high` | 1 |
| `medium` | 4 |
| `low` | 24 |

Используйте стандартные возможности n8n или собственную логику: **способ построения схемы не регламентирован**, проверяется результат. Убедитесь, что после HTTP Request вы не потеряли поля исходного обращения.

## 6. Этап 3. Зарегистрировать обращение и вернуть ответ

Сформируйте объект для `POST http://mock-api:8080/requests`, включив:

`requestId`, `userId`, `userName`, `department`, `type`, `priority`, `description`, `assignedGroup`, `slaHours`, `status: "registered"`.

Только **после успешной регистрации** верните **HTTP 201**:

```json
{
  "requestId": "REQ-1024",
  "status": "registered",
  "assignedGroup": "Technical Support",
  "slaHours": 1,
  "userName": "Иван Иванов"
}
```

Результат должен **фактически присутствовать** в Mock API. Тесты проверяют сохраненные данные, поэтому простая выдача заранее заготовленного ответа не подходит.

Для двух **разных** обращений данные не должны смешиваться.

## 7. Этап 4. Ошибки внешних сервисов

Настройте корректное поведение в следующих случаях:

- `GET /users/{id}` вернул `404` — Webhook отвечает `404 USER_NOT_FOUND`, регистрация не вызывается;
- получение пользователя вернуло `5xx` — `502 UPSTREAM_ERROR`, без регистрации;
- регистрация вернула `4xx/5xx` — `502 UPSTREAM_ERROR`, без ложного успешного ответа.

Для ошибок используется единая структура:

```json
{
  "error": {
    "code": "UPSTREAM_ERROR",
    "message": "Не удалось выполнить запрос к внешнему сервису"
  }
}
```

`message` должна быть непустой строкой; точный текст не оценивается. **Retry пока не требуется.**

## 8. Этап 5. Самопроверка и оформление (обязательно)

1. Сохраните и **опубликуйте** workflow. Для тестов используется Production URL `/webhook/support-request`, не `/webhook-test/...`.
2. Не допускайте публикации двух workflow с одинаковым путем Webhook.
3. Из корня репозитория выполните:

```shell
python tests/run_tests.py --mode base
```

4. Посмотрите `reports/latest-results.md`. Всего **18 групп**, суммарно **60 баллов** за функциональность.
5. Исправьте ошибки либо опишите оставшиеся ограничения в `REPORT.md`.
6. Переименуйте узлы так, чтобы было понятно их назначение; оставьте пояснения к нетривиальной логике.
7. Экспортируйте ваш основной workflow в `submissions/support-request-workflow.json` (создайте каталог, если его нет). **Не** отправляйте экспорт обучающего примера вместо решения.

Тестовый скрипт сбрасывает данные Mock API перед сценариями. Не делайте параллельных ручных запросов во время тестов.

## 9. Дополнительная часть для уровня Э (до 2–3 часов)

Выполняется **после** базовой части. В отличие от учебного практикума, здесь не дается пошагового алгоритма и не предписываются конкретные узлы. Студент самостоятельно исследует возможности n8n и выбирает реализацию.

### Задание Э-1. Управляемые повторные попытки при сбое

Дополните **регистрацию** обращения так, чтобы при временном `HTTP 503` операция повторялась. Ограничения:

- **не более 3 вызовов всего** (исходный + до 2 повторов);
- между повторными запросами после `503` — задержка **не менее 0,4 секунды**;
- при `400` повторно обращаться **нельзя**;
- если все попытки завершились `503`, Webhook возвращает `502 UPSTREAM_ERROR`;
- если сервис восстановился на второй или третьей попытке, регистрация завершается `201` и появляется ровно одна запись.

Демонстрируйте корректность через тесты: один успешный ответ без Retry не означает, что механизм работает. **Подсказка уровня постановки:** различайте временные и постоянные ошибки и следите за количеством фактических вызовов API.

### Задание Э-2. Защита от повторной регистрации

Два последовательно поступивших обращения с одним и тем же `requestId` **не должны создавать две записи**. Для второго запроса нужен `HTTP 200`:

```json
{"requestId":"REQ-1024","status":"already_registered"}
```

Следующее обращение с **другим** `requestId` должно обрабатываться как новое. Гонки между одновременными запросами не проверяются. Mock API сам **не** предотвращает дубликаты.

Проверка дополнений:

```shell
python tests/run_tests.py --mode expert
```

Все восемь экспертных проверок необходимы для уровня Э. Дополнительная часть не компенсирует ошибок базовой.
